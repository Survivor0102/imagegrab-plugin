# 小皮筋“图片 / 名称筛选”实测记录

实测日期：2026年11月6日  
插件版本：ImageGrab 1.8.2  
测试平台：1688  
操作方式：普通 Chrome 已登录会话，通过 CDP 后台操作；没有接管系统鼠标。

## 一、测试目标

本次用截图中的商品作为参考，目标是寻找“小桶装一次性黑色小皮筋”，原图及商品文字中包含“35根/罐、20克/罐”等信息。

裁剪参考图已归档至 `evidence/2026-11-06/hair-tie/reference.png`，原始截图已归档至同目录 `source-screenshot.png`。

本次设置如下：

| 条件 | 设置 |
|---|---|
| 名称 | 桶装 黑色 小皮筋 |
| 品类 | 皮筋 发圈 头绳 |
| 匹配模式 | 可接受其他品牌的相似替代品 |
| 参考图 | 已上传并使用裁剪区域 |
| 数量上限 | 10 |
| 品牌、型号、必需词、排除词 | 未填写 |

没有把“35根/罐”和“20克/罐”填入自动筛选条件。当前规格解析器只对 mm、cm、W、V 等单位做规则判断，不能把“35根”和“20克”作为可靠的自动规格条件，所以这两项放到详情页人工核对。

## 二、实际操作顺序

### 1. 上传参考图

先把此前筒灯测试的候选池备份到 `previous-pool-backup.json`，再清空独立候选池开展本次测试，已有221件研究档案保留。随后在插件的“选品研究台 → 图片 / 名称筛选”中上传参考图，确认页面显示已上传 1 张图片。参考图主体是透明细长筒内的黑色皮筋。

### 2. 进行图片搜索

点击“打开1688图片搜索”。插件把图片写入 1688 图片搜索页的原生文件入口，但这次平台页面没有自动提交，因此又在图片搜索页实际点击了“搜索图片”按钮，进入真正的图片搜索结果页。

随后从图片搜索结果页读取候选卡片，得到 60 条原始记录。

### 3. 进行名称搜索

点击“打开1688名称搜索”。插件通过 1688 原生搜索框输入“桶装 黑色 小皮筋”，没有手工拼接中文搜索 URL。

名称搜索页读取了 100 条记录。名称结果内部存在同一商品的重复记录，例如同一商品的不同卡片链接或合成链接，因此不能把这 100 条直接当成 100 件独立商品。

### 4. 合并和去重

图片搜索和名称搜索结果按商品详情链接及商品 ID 规范化去重，并保留每个商品来自哪一路搜索。

| 阶段 | 数量 |
|---|---:|
| 图片搜索原始记录 | 60 |
| 名称搜索原始记录 | 100 |
| 两路合并后的唯一候选 | 110 |

进一步核查来源记录后，本次图片渠道为60件、名称渠道为50件，两个渠道未记录到相同商品ID。名称搜索返回的100条内部去重成50件；本次110件来自60+50，并非两路各有50件交集。

候选字段也有不完整处：110件中有50件的结构化价格字段为空，5件供应商字段为空。名称卡片的可见文字仍可能含价格及供应商名称，说明当前模板的字段提取存在缺口，不能直接理解为商家没有展示。这些空字段不参与当前排序规则，也不是进入“待确认”的判定条件。

### 5. 文字初筛

插件先检查标题是否命中品类词，再检查名称片段。当前名称被拆成“桶装、黑色、小皮、皮筋”4 个片段。

这一阶段排除了 34 条标题不满足品类条件的记录，剩余 76 条进入图片读取和外观比对。例如发膜、手机三脚架、美甲碎石、花束包装纱网都未命中“皮筋 / 发圈 / 头绳”。一字夹虽然同属发饰，也会因为未命中设定品类被排除；这是本次规则范围的结果。

### 6. 本地图片比对和排序

插件从候选记录中读取商品图片，在本地进行像素级外观比较，没有调用外部 AI API。每个候选最多取前两张图片。

本地外观分由三部分组成：

- 64 位差分哈希：45%；
- 16×16 灰度空间布局：40%；
- RGB 颜色直方图：15%。

图片分是外观相似度的排序依据，不是“同款概率”，也不能识别“是否 35 根、是否 20 克”。本次76个进入图片比对的候选都至少得到了一张可用于比对的图片；其中22件的另一个图片链接读取失败。界面显示“76件比对、22件读取失败”，这两项有重叠，不能理解成76件成功加22件完全失败；候选图片列表混入SVG等页面资源，是已知的干扰来源。

当前条件下，排序分的计算方式是：品类命中加30分，名称片段命中比例乘25后四舍五入，外观分乘0.3后四舍五入再相加。是否进入优先候选还要单独检查图片分是否达到70；不能仅按总分高低理解分组。

最终结果：

| 结果类别 | 数量 |
|---|---:|
| 优先候选 | 1 |
| 待确认 | 75 |
| 已排除 | 34 |

## 四、这次实际收集到了什么

本次详情补全任务共处理 2 件商品，任务状态为 `complete`，研究档案商品数量从 221 件增加到 223 件。每件详情主要收集了：

- 商品详情链接、标题和来源搜索渠道；
- 供应商名称、供应商主页、发货地；
- 卡片价格、价格上下文、起批信息；
- 页面显示销量及其来源页面；
- 店铺经营年限、主营类目、部分店铺指标；
- 商品属性，包括品牌、材质、产地、包装、颜色等；
- SKU 规格、每个规格的价格、库存和规格图片链接；
- 主图、详情图、SKU 图和视频链接；
- 页面包装参数；
- 证书字段是否出现。当前两件商品的证书状态都是“仅记录页面参数，未进行官方认证核验”。

当前保存的图片主要是媒体链接和 SKU 图片链接；这次没有把全部媒体链接都下载成项目文件夹中的图片文件。因此，报告中的“有 50 条 / 23 条媒体记录”表示已采集的链接记录，不等于已经下载了 50 / 23 个本地图片文件。

## 五、结论和边界

这次由我选择参考图、设置关键词、补点1688“搜索图片”按钮，并指定两件货源进入详情队列；候选读取和详情队列通过插件现有的 `SOURCING_CAPTURE`、`SOURCING_UPDATE`、`SOURCING_ENRICH` 消息通道触发，与页面对应操作共用后台逻辑。图片与名称检索没有合并成带全部关键词的单次搜索。

我选择第二件待确认货源，是为了对照“名称匹配高、图片分不足”的情况；这一步是本次人工选样，不能声称插件自动选中了两件最合适的商品。截图中商品的包装数量及重量，也是本次进一步核对得出的限制，并非当前评分器自动判定出的结果。

这次实际验证了插件下列能力：

1. 读取参考图片并打开 1688 图片搜索；
2. 用名称打开 1688 搜索并读取结果；
3. 合并两路候选并按商品链接去重；
4. 按品类、名称片段和本地图片外观分进行排序；
5. 按选中的商品链接进入详情页补全供应商、发货地、SKU、价格、库存、规格图片和详情媒体链接；
6. 把“优先候选”和“待确认候选”区分开。

这次也验证出当前版本不能自动保证以下结论：

- 不能仅凭图片分确认是同款；
- 不能仅凭标题确认包装内有 35 根；
- 不能把“20克/罐”自动当作筛选条件；
- 不能把卡片价格直接解释成目标 SKU 的最终采购价；
- 不能把页面参数直接当作官方 CCC 等认证证明；
- 图片链接被采集不等于图片文件已经下载到本地。

因此，本次两件货源都应标记为“候选货源，尚未确认同款”。其中候选一更接近“中桶黑色”规格，候选二的标题更接近“黑色桶装”，但规格实际为“混色随机”。
